### Shipping

Resolve the driver skill through [poteto-mode's Non-negotiables](../SKILL.md#non-negotiables).

You own what lands. Land one verified PR at a time, then confirm its outcome before advancing. This is the half after `playbooks/babysit.md`; it requires the user's landing authority.

1. **Resolve the forge and dependency chain.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use it and record that choice. Otherwise record the GitHub fallback. Never require Graphite (`gt`). Capture the affected chain bottom-to-top, each head branch and SHA, base branch and SHA, and the intended destination repository and branch. Leave unrelated PRs alone. Inspect pending requests on entry. Cancel and read back any that lack the durable verification gates in step 8 before starting a lengthy review. Reconcile any merge that races cancellation. Read [Merge and restack safety](../references/merge-safety.md) before merging, arming, rebasing, or retargeting.
2. **Verify each PR independently.** One subagent per PR, each in its own worktree, exercises the real surface through the driver skill against parent versus head. Each returns `PASS`, `PASS+NOTES`, or `FAIL` and posts that verdict on its own PR. The verifier must not have written the code. CI green and an approving bot review do not replace this verdict. Record the verdict's head SHA, base SHA, base branch, and stable `git patch-id` of the base-to-head diff.
3. **Find the contiguous verified run.** Walk from the lowest unmerged PR and stop at the first without `PASS` or `PASS+NOTES`. Report that ceiling. A verified child above an unverified parent cannot land yet.
4. **Cancel pending merges before changing the chain.** Establish which PRs a rewrite or retarget can affect, including dependent descendants. Run the canonical `ship-pr inspect` and `ship-pr cancel-pending` operation from [Merge and restack safety](../references/merge-safety.md) for each affected PR. Require a successful `cancelled` result before any branch push, rebase, or base edit. The command handles both automatic requests and queue membership, with complete revision validation and readback. If cancellation fails, state is unavailable, or a PR merges during cancellation, stop the rewrite and reconcile actual state first. Coordinate with other topology writers so they do not rearm the chain during the operation.
5. **Prepare only the bottom PR.** Fetch current trunk. After a parent squash, use the recorded old parent boundary to replay only the child's own commits, as in the safety reference. Publish a rewrite with an explicit lease against the remote SHA captured before rewriting. Retarget only this PR to trunk. Do not prepare or arm descendants yet.
6. **Reassess the evidence.** Any changed head or destination invalidates the old readiness observation. Compare the current diff and context with the recorded verdict. When the two patches differ only in tests, docs, or lint config, build what each lane ran. Build it twice at the verdict SHA and once at the current head. A difference is noise if the two builds at the verdict SHA also show it, or if it is an embedded commit SHA. Judge each difference, not each file, and report each kind of noise with its files. If only noise differs, that lane's result stays valid, and checks and a review of the change run fresh. Do not reuse a lane result from a dev server or from anything else with no build output. Rerun that lane. A matching patch-id may preserve substantive code review after a history rewrite, but does not prove the review applies to a different destination or changed dependencies. Re-verify changed behavior or uncertain applicability. Always rerun current checks and mergeability after a rewrite or retarget. Capture the exact head and destination now approved to land.
7. **Merge with a service-enforced head condition.** For an immediate GitHub merge, use `gh pr merge <pr> --repo <owner/repo> --squash --match-head-commit <verified-head>`. A last-second read without this condition leaves a race. Confirm the destination immediately before requesting the merge. GitHub's head guard does not atomically guard the base branch. If concurrent retargeting cannot be controlled, stop and resolve ownership. Never claim an atomic destination guarantee. Origin may be used only after its installed CLI/API proves an equivalent server-side head condition. Do not guess a flag or fall back to an unguarded merge. If unavailable, report the limitation and use an explicitly resolved supported forge path or stop at merge-ready.
8. **Arm future merging only with durable verification gates.** `--auto` and queue admission are future actions. A head check at admission does not prove a later head is approved. Require repository rules that enforce the needed verification on the revision and context that will land, including the independent verdict and required CI. Confirm that stale approval cannot authorize a changed revision. Never change protection settings to satisfy this step. Without those gates, keep watching and issue a guarded immediate merge when ready. A queue-required branch can turn even a plain `gh pr merge` into queue admission or auto-merge. Inspect that policy first and use the same gate requirement. Never use `--admin` to bypass it.
9. **Watch the frontier and preserve its verdict.** With GitHub, run `skills/poteto-mode/scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom>` under the installed plugin. With Origin, use `origin pr view <pr> --checks --comments` and `origin pr checks <pr> --watch`, then reread the PR. Hold the watch under `/loop` in dynamic mode. Do not add a second sleep loop. At watcher wakeups, compare the complete landing revision, including the base OID, with the approved record through `ship-pr inspect`. Inspect both pending merge mechanisms. Cancel stale requests when evidence no longer applies, and reassess. Polling cannot protect the interval between wakeups. The gates in step 8 must block unverified revisions then.

   The watcher owns GitHub blocker classification. Preserve `BLOCKER` reasons and route them through `playbooks/babysit.md`: conflicts to the topology owner, threads and CI to the PR owner, human approval gates to a wait. Do not rearm an unchanged blocker. `WAITING`, including `merge-queue`, is non-terminal. Pending checks are neither failure nor completion. Diagnose `TIMEOUT` and `status-query` blockers; unknown state never permits a merge. A required check failing after queuing needs intervention, not advancement.
10. **Confirm the landing before advancing.** `COMPLETE` is a prompt to confirm actual state, not sufficient evidence of the destination. Read the PR's merged state, final head, base branch, and merge commit; fetch the intended destination and confirm that merge commit is in its history. Compare with the approved record and inspect the resulting content. A queued or scheduled response is not a merge. If any result contradicts the verified landing, stop the chain. Otherwise drop the merged PR from the frozen list, preserve its old head as the child's exclusion boundary, and repeat from step 4 for the new bottom. Do not assume the host retargeted the child correctly.
11. **Stop at the ceiling.** Report what landed and what the next unverified PR needs. Extending the verified run is a new pass through step 2.

**Reply:** the verified run and ceiling, verdicts and their head/destination records, what was armed or cancelled and read back, confirmed landings, and unresolved state or service limits.
